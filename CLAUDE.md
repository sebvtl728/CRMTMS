# TMS sur mesure — guide pour Claude

TMS (Training Management System) multi-organismes pour organismes de formation, inspiré de Formdev. Premier client : CAP FORMATION (SCOP). Produit destiné à être vendu à d'autres organismes.

## Documents de référence

- Spécifications sources : `Cdc/Cartographie projet – TMS sur mesure.md` (périmètre TMS complet) et `Cdc/cdc-activité-commercial.md` (gestion commerciale détaillée).
- Conception validée : `docs/superpowers/specs/2026-11-11-tms-design.md` — **autorité** en cas de doute.
- Plans d'implémentation : `docs/superpowers/plans/` (un plan par incrément : 1a socle, 1b fiches/import, 1c pipeline, 1d devis, 1e pilotage). Documentation d'exploitation et utilisateur : `tms/docs/` (`install`, `admin`, `crm`, `sessions`, `connectors`, `data-dictionary`, `release`).

## Stack

Laravel 12 (PHP 8.4) + Inertia + React 19 / TypeScript + Tailwind/shadcn ; PostgreSQL 17 ; Redis + Horizon ; Gotenberg (PDF) ; Caddy ; Docker Compose. Tests : Pest, Playwright, bats. Application dans `tms/`, CI à la racine (`.github/workflows/`).

Code métier par module : `tms/app/Modules/<Module>/` (`Core/…`, `Connectors/…`, puis `Crm`, `Sessions`, `Finance`, `Qualite`…). Un module ne lit pas les tables d'un autre : services publics ou évènements.

Moteur Docker local : Colima (`colima start` si `docker info` échoue).

Scripts d'exploitation (installation, mise à jour, sauvegarde, publication) : `tms/ops/` (tests bats : `tms/ops/tests/`) ; publication : `.github/workflows/release.yml`.

Installation dev complète : `tms/docs/install.md`. App : http://localhost:8080, santé : `/health`.

## Règles à ne jamais enfreindre

1. **Isolation multi-organismes** : toute table métier a `tenant_id uuid not null`, le trait `BelongsToTenant` et une politique RLS (`Rls::enable`). Le test d'architecture échoue sinon. L'application se connecte en `tms_app` (non propriétaire, `NOBYPASSRLS`) ; seules les migrations utilisent `tms_owner`. Les jobs en file portent le tenant (`TenantAwareJob`).
2. **Aucun secret** ni mot de passe par défaut dans le dépôt ; `.env` est généré (installateur) et ignoré par git.
3. **Français** pour toute l'interface et les messages utilisateur ; formats français (dates, montants, CSV `;`).
4. **Sécurité** : cible OWASP ASVS niveau 2 ; mots de passe Argon2id ≥ 12 caractères ; 2FA obligatoire pour admin et direction ; journal d'audit append-only ; secrets des connecteurs chiffrés.
5. **Connecteurs** : tout logiciel externe (Formevol, Sage, SoWeSign, Outlook…) passe par un adaptateur isolé dans `app/Modules/Connectors`, jamais codé en dur dans le métier.
6. **TDD** : test d'abord, puis code ; tests verts avant chaque commit.
7. Listes métier (DAS, étapes, origines…) = **référentiels paramétrables par organisme**, jamais des constantes en dur. Un module stocke l'**id** de la valeur (clé étrangère vers `reference_items`), jamais son code, et déclare la colonne avec `ReferenceUsage::register(...)` (une valeur utilisée ne se supprime pas).
8. **Cache** : toute clé contenant des données d'un organisme est préfixée par l'id du tenant.
9. **Files d'attente** : jobs et notifications reçoivent le tenant automatiquement par leur charge utile ; ne jamais appeler `TenantContext::set` de façon globale dans un worker.
10. Tout nouveau modèle sur une table métier utilise `BelongsToTenant`.

## Module Crm (lots 1b et 1c) : points d'architecture à connaître

Code dans `tms/app/Modules/Crm/` (Organisations, People, Affiliations, Opportunities, Activities, Dashboard, Timeline, Duplicates, Search, Export, Import, Gdpr, Visibility, Support). Guide utilisateur : `tms/docs/crm.md` ; tables : `tms/docs/data-dictionary.md`.

- **Historique** : chaque source est un `TimelineProvider` taggé `Timeline::TAG` dans `CrmServiceProvider::register()` (notes, pièces jointes, audit, étapes d'opportunités, actions). Un futur module (devis…) ajoute son fournisseur au tag, sans toucher au Crm. Pagination par **curseur composite opaque** (`TimelineCursor` : instant µs, type, id) : un fournisseur filtre avec `Timeline::after($query, $before, 'type', 'colonne_date')` ; un curseur mal formé renvoie la première page.
- **Données liées** : `Support\LinkedData::register('module.cle', fn ($fiche, $exceptIds) => bool)` déclare ce qui rattache une fiche (rattachements, notes, opportunités, actions…) ; l'annulation d'un import la conserve si `LinkedData::any()` est vrai. Même principe pour le dernier contact : `Timeline\LastContact::registerSource()` (les actions faites y contribuent) et `LastContact::recompute()` après suppression.
- **Opportunités** (`Opportunities/`) : compte = entreprise **ou** particulier (CHECK, une personne non particulier est refusée) ; tout changement d'étape passe par `OpportunityStage::move()` (motif obligatoire pour perdu, gagné/perdu forcent 100/0, historique `opportunity_stage_changes`, `probability_overridden` gardé un seul déplacement) ; issue d'une étape = `meta.outcome` (`won`/`lost`) du référentiel, jamais un code. `OpportunityListQuery::build()` est l'unique requête (liste, kanban, export, accueil) : périmètre (`CrmVisibility`) et fiches en corbeille exclues.
- **Actions** (`Activities/`) : visibilité (`CrmVisibility::activities`) = celle de l'opportunité si `opportunity_id`, sinon celle d'une fiche liée. `TodoQuery` (jours de Paris, badge en cache 60 s préfixé tenant, `onLiveFiches()`), `WeekPlanning::types()` lit le drapeau `meta.planning` (`meeting`/`call`) des types d'action — jamais de code de type en dur côté serveur. Création/complétion via `ActivityRecorder` (relance suivante incluse) ; `QuickReport` fait tout dans une transaction. L'évènement `Activities\Events\ActivityChanged` (après commit) est la seule porte vers Outlook ; le module Connectors lit les actions par `CalendarEvents` (service public, sans compte rendu).
- **Collaborateurs** (`Activities\ActivityCollaborators`, table `activity_collaborators`) : utilisateurs actifs ayant `crm.activities.view` (jamais un nom de rôle) ; « Attribuer à » multiple (premier = responsable) ; voient et modifient par `CrmVisibility::activities` (groupe OR, droits « Consulter » et « Modifier », jamais « Supprimer ») et `allows`, `TodoQuery` et `WeekPlanning` les incluent ; `ActivityStats` les exclut (`collaborators: false`).
- **Statistiques** : `Dashboard\ActivityStats` (12 mois de Paris : actions créées, réalisées, RDV fixés = types `meta.planning` « meeting » par `created_at`), carte de l'accueil.
- **Accueil** : `Dashboard\CommercialSummary` (relances, pipeline pondéré du mois de Paris, prochains RDV) réutilise `TodoQuery`, `OpportunityListQuery` et `WeekPlanning` ; accessible dès qu'un des quatre droits « Consulter » du CRM est détenu (`Permissions::anyView`) ; chaque bloc suit le périmètre de son domaine, et la carte « CA signé » exige `crm.revenue.view`.
- **Tenancy hors requête** : `ForEachTenant::run()` pour tout traitement planifié ou de maintenance (une erreur sur un organisme n'arrête pas les autres) ; `TenantStorage` pour tout chemin de fichier (`tenants/<tenant_id>/<zone>/`, disque privé) ; jamais de chemin construit à la main. `PermissionSync` (`tms:permissions:sync`, lancé par `ops/migrate.sh`) accorde **une fois** les nouveaux droits par défaut de chaque rôle ; un module déclare ses permissions via `Core\Access\Permissions::registerModule()` dans `register()` (avant `AccessServiceProvider::boot`).
- **Types polymorphes** : `MorphAliases::register()` par module, `enforceMorphMap` actif : un modèle sans alias lève une exception ; on stocke l'alias (`organisation`, `person`…), jamais la classe.
- **RLS et fonctions non « leakproof »** : sous FORCE RLS, un index d'expression (`lower()`, `unaccent()`, `regexp_replace()`, `@>` jsonb) n'est pas utilisé. Les clés de recherche et de doublons sont donc des **colonnes générées stockées** (`search_vector`, `dup_*`) comparées par `=` ; `import_stamps` remplace une recherche jsonb. Ne pas réintroduire d'index d'expression sur une table RLS sans vérifier le plan (`EXPLAIN`) avec le rôle `tms_app`.
- **Fuseau** : le fuseau PostgreSQL de session suit `APP_TIMEZONE` (`Europe/Paris`, `config/database.php`) : dates, `now()` SQL et PHP concordent. Ne jamais comparer des horodatages sans fuseau.
- **Connecteurs sortants** : toute adresse appelée (SMTP, Sirene…) passe par `Connectors\Core\HostPolicy` (adresses internes/privées refusées, vérifié à l'enregistrement et à l'appel).
- **Import** : `Import/` lit CSV/XLSX en continu, simule puis exécute par tranches reprenables (files `imports` et `default`, `TenantAwareJob`). `ImportStamps` (table `import_stamps`) enregistre ce que chaque import a fait à chaque fiche : c'est ce qui permet d'annuler sans écraser le travail des utilisateurs. Un import Formevol = un enregistrement `import_profiles`, pas de code.
- **Erreurs** : un message affiché à l'utilisateur doit lever `App\Exceptions\UserFacingHttpException` (message en français) ou passer par une erreur de validation ; un `abort()` simple n'affiche que le texte fixe de son code.
- **Données personnelles** : aucune valeur de champ personnel en clair dans `audit_logs` (`Auditable::$auditPersonal`, valeur `[donnée personnelle]`) ni dans les logs ; l'anonymisation (`Gdpr/Anonymiser`) purge aussi les lignes d'import et les pièces jointes.
- **Visibilité** : toute requête sur une fiche passe par `CrmVisibility`, piloté par le **périmètre** du droit (voir « 0.5.0 : droits et rôles ») et non par le nom du rôle ; les `Route::bind` du `CrmServiceProvider` renvoient 404 pour une fiche hors périmètre de consultation.

## Modules Catalogue et Devis (lot 1d) : points d'architecture à connaître

Guide utilisateur : `tms/docs/crm.md` (§ 4 catalogue, § 5 devis) ; réglages : `tms/docs/admin.md` (§ 3 sociétés, § 14 devis).

- **Catalogue** (`tms/app/Modules/Catalogue/`, tables `trainings`, `training_funding_modes`, permissions `catalogue.view` / `catalogue.manage`) : module à part. Le Crm n'en utilise que `Trainings` (service public : `find`, `options`, `search`, import), `TrainingData` (tarifs en centimes entiers) et `TrainingUsage`, et ne nomme jamais ses tables (`ModuleBoundariesArchTest`, motif `CATALOGUE_TABLES` : pas de clé `'trainings'` nue dans le Crm, d'où `training_lines`, `options.training`, `training_titles`). Catalogue ne dépend pas du Crm (exports partagés dans `Core\Exports`).
- **TrainingUsage** : registre de garde-fous de suppression. Tout module qui référence une formation s'y déclare (`TrainingUsage::register('nom', fn ($id) => bool)`, comme `opportunities` et `quotes` dans `CrmServiceProvider`) ; la suppression d'une formation et l'annulation d'un import le consultent.
- **Devis** (`tms/app/Modules/Crm/Quotes/`) : `QuoteTotals` calcule tout en centimes entiers avec `brick/math` (jamais de float ; TVA par taux sur la somme des lignes, arrondi demi supérieur) ; `QuoteWriter` crée et modifie un brouillon dans une transaction ; `QuoteNumbering::next()` exige une transaction et incrémente `quote_sequences` clé (`tenant_id`, `prefix`, année de Paris) ; `quote_prefix` unique par organisme. Un devis non brouillon ne se modifie plus (409).
- **Transitions** : `QuoteTransitions` (verrou `lockForUpdate` sur chaque transition) : envoi = `QuoteFreezer::freeze` (destinataire figé, PDF archivé, régime de TVA figé) puis `SendQuote` (`TenantAwareJob`, `afterCommit`, `TenantMailer`, `email_status`) ; l'opportunité avance vers l'étape `meta.quote_stage` (`OpportunityStage::quoteStage()` / `advanceTo()`, jamais un code d'étape en dur) ; « Gagné » reprend le montant du devis accepté lu côté serveur (`quote_id` sur l'endpoint d'étape). Expiration : `tms:crm:expire-quotes` (0 h 05 Paris, `ForEachTenant`).
- **PDF** : `Core\Documents\PdfRenderer` (Gotenberg, `config/documents.php`, `GOTENBERG_URL`) est le seul moteur ; `QuotePdf` + `resources/views/documents/quote*.blade.php` (CSP sans ressource externe, logo en data URI, `{{ }}` seulement). Un devis envoyé sert toujours son archive (`TenantStorage` zone `quotes`) ; sans archive : 410, jamais de nouveau rendu. Échec Gotenberg = `PdfRenderingFailed` (503, message français).
- **Données personnelles** : `recipient_snapshot`, `notes`, `refusal_reason` dans `$auditPersonal` ; `email_*` hors audit ; échecs SMTP sans texte du serveur (`QuoteMailFailed`) ; `QuoteAnonymisation` (appelé par l'Anonymiser) efface aussi les PDF archivés.
- **Taux de réussite** : `QuoteSuccessRate` passe par `QuoteListQuery` (même source que la liste et l'export : filtres et périmètre).

## 0.5.0 : droits et rôles : points d'architecture à connaître

Guide : `tms/docs/admin.md` (§ 10), `tms/docs/crm.md` (§ 13 bis).

- **Périmètres** (`Core\Access\AccessScope` : `own`, `das`, `all` ; table `role_permission_scopes`, sans ligne = `all`) : un module déclare ses droits avec `Permissions::registerModule(..., $scoped, $defaultScopesFor)` (`scoped` = droits à périmètre, `defaultScopesFor` = périmètre par défaut par rôle système). « Ses fiches » = `responsible_user_id` **ou** `created_by` ; un devis suit son opportunité ou son créateur. Un droit détenu **seulement** par une permission directe de l'utilisateur (`model_has_permissions`, sans rôle qui le porte) a le périmètre `all` (`Scopes::of`) ; aucun écran n'accorde de permission directe.
- **`CrmVisibility`** : chaque méthode prend le **droit** (`Permissions::FICHES_VIEW`, `…_UPDATE`, `…_DELETE`…) et en lit le périmètre de l'utilisateur ; `allows($user, $permission, $record)` répond pour un enregistrement. Le périmètre de modification peut être plus large que celui de consultation : la fiche hors périmètre de consultation reste en 404. **Aucun test sur un nom de rôle** dans le code métier (ni `hasRole`, ni `Role::…` hors des droits par défaut) : tout passe par un droit et son périmètre.
- **Import** : `RowImporter` ne complète ni ne rattache une fiche existante (doublon, identifiant source, sujet d'une note) hors du périmètre `crm.fiches.update` de l'utilisateur qui a lancé l'import (`ImportBatch::user`) : la ligne est ignorée (`RowImporter::OUT_OF_SCOPE`), sans créer de doublon.
- **Rôles personnalisés** : `RoleCatalogue` (création, renommage, 2FA, suppression ; libellé unique sérialisé par verrou) ; un rôle personnalisé est nommé `custom_<uuid>` (`roles.name`, jamais affiché), son libellé est `roles.label`, `roles.system` distingue les six rôles système (jamais supprimés), `roles.requires_2fa` règle la 2FA (toujours vraie pour `admin_organisme` et `direction`, dans `RoleModel::requires2fa()` aussi). `Permissions::LOCKED` n'est jamais accordé à un autre rôle. Un rôle ne se supprime pas tant qu'un utilisateur (actif ou désactivé) ou une invitation non expirée le porte.
- **`RoleScopesChanged`** : évènement émis (après commit) quand les périmètres d'un rôle changent ; le Crm l'écoute (`FollowedDas`) pour la page Utilisateurs (DAS suivis). `PrimaryRoleChanged` couvre le changement de rôle d'un utilisateur.
- **Migration des droits** (`2026_12_06_000002_split_crm_permissions`) : organisme par organisme (`set_config('app.tenant_id', …)`), convertit les anciens `crm.view|create|update|delete` ; `tms:permissions:sync` n'accorde ensuite que les droits par défaut **nouveaux** (`role_permission_defaults_applied`).
- **Chiffre d'affaires** (`tms/app/Modules/Crm/Revenue/`) : `DasRevenue::for($user, Period)` en **centimes entiers** (`brick/math`, jamais de float), jours de Paris ; un devis compte à `accepted_on` par le `das_id` de sa ligne (jamais le Catalogue), une opportunité gagnée à `won_on` **seulement sans devis accepté** (jamais deux fois), corbeille exclue, ligne sans DAS = DAS de l'opportunité. `RevenueSources` applique le périmètre de `crm.revenue.view` ; `RevenueTargets` : un objectif par DAS et par type de période (`revenue_targets`, pas de somme des mois). Le taux « Atteint » du total (`totals.rate`, serveur) compare l'objectif au seul CA des DAS qui en ont un (`targeted_total_cents`).

## Plaquettes (0.5.2) : points d'architecture à connaître

Guide : `tms/docs/crm.md` (§ 4 et § 5) ; tables : `tms/docs/data-dictionary.md`.

- **Bibliothèque** (`Catalogue/Brochures/`, `Catalogue\Brochures` service public) : plaquettes + versions PDF immuables (une version envoyée ne s'efface jamais) ; les autres modules les lisent par ce service (`forTrainings`, `versions`, `offered`, `sent`, `options`), jamais par les tables. `Brochures::registerSentCheck()` : le Crm déclare « version envoyée » (`quote_brochures`, `brochure_sending_versions`) pour que le téléchargement d'une version envoyée d'une plaquette à la corbeille reste possible (sinon 404).
- **Devis** : `quote_brochures` garde les versions jointes à l'e-mail ; relance et « Renvoyer » rejoignent les mêmes versions. **Envoi depuis une fiche** (`Crm/Brochures/`) : `brochure_sendings` + `brochure_sending_versions`, `SendBrochure` (`TenantAwareJob`), modèle d'e-mail `brochure`, historique par `BrochureSendingsProvider`, effacé par l'anonymisation.
- `BrochureAttachments` : limite commune de 20 Mo par e-mail et lecture des fichiers ; les deux e-mails partent en texte simple (vue `mail/plain-text`).

## Module Sessions (lot 2a) : points d'architecture à connaître

Code dans `tms/app/Modules/Sessions/` (Sessions, Dossiers, Enrolments, Fundings, Gdpr, History, Settings). Guide utilisateur : `tms/docs/sessions.md` ; réglages : `tms/docs/admin.md` (§ 15) ; tables : `tms/docs/data-dictionary.md`. Spec : `docs/superpowers/specs/2026-11-15-lot2a-dossiers-sessions-design.md`.

- **Frontières** : Sessions n'atteint le CRM que par `Crm\Public\*` (`Fiches`, `Trainees`, `AcceptedQuotes`, `UserDas`, `FicheBlocks`, `QuoteLinks`, `FicheLinks`, `FicheHistory`) et le catalogue que par `Trainings`, `TrainingData`, `TrainingUsage` ; il ne nomme aucune table du CRM ni du catalogue (`ModuleBoundariesArchTest`, `CRM_TABLES`). Crm, Catalogue, Core et Connectors n'importent jamais Sessions : le module se déclare dans leurs registres (`SessionsServiceProvider::boot`).
- **Registres du CRM** (`Crm\Public`) : `FicheBlocks` (blocs « Formations suivies » / « Dossiers » des fiches), `QuoteLinks` (« Créer le dossier » d'un devis accepté), `FicheLinks` (données liées pour l'annulation d'un import → `LinkedData` ; repointage à la fusion, appelé par `Merger` dans sa transaction et pouvant la refuser par une erreur de validation ; anonymisation, appelée par l'`Anonymiser` ; sections de l'export RGPD et droits « Consulter » exigés sur « Tout » par `PersonDataExport::allowedFor`), `FicheHistory` (entrées d'historique d'un type, lues par `Crm\Timeline\ModuleHistoryProvider` ; la source filtre avec `$request->after($query)` pour le curseur).
- **États** = enums dans le code (`DossierStatus`, `SessionStatus`, `EnrolmentStatus`, `FundingStatus`) ; listes métier = référentiels (`funding_type`, `abandon_reason` avec `meta.force_majeure`, `cancel_reason`, `bpf_category`, `education_level`, `training_modality`). « En cours » / « Réalisé » / « Terminée » se calculent à la lecture (`effective()`, jours de Paris) ; `DossierSchedule::spans()` lit les dates pour une page entière.
- **Écritures** : `SessionWriter`, `DossierWriter`, `DossierTransitions`, `Enrolments` (sous verrou du dossier et de la session ; liste d'attente sans promotion automatique ; heures prévues par stagiaire 0 < h ≤ heures de la session), `GroupEnrolment` (plusieurs stagiaires d'une ligne en une transaction via `Enrolments::enrol`, personnes créées une fois par `ref`, erreurs `trainees.<j>[.<champ>]`, tout ou rien), `PriceShares` (répartition au centime, reste aux premières inscriptions), `FundingWriter` (verrou du dossier). Numérotation `D-`/`S-<année Paris>-<NNNN>` (`DossierNumbering`, `SessionNumbering`, mécanique de `QuoteNumbering`). `DossierFromQuote` : un dossier par devis (unique `quote_id` + verrou), tout en une transaction.
- **Libellé d'une session** : `TrainingSession::label($titreFormation)` = « <intitulé ou formation> (S-…) » ; l'intitulé (`title`, facultatif) est cherché par la liste.
- **Montants** : centimes entiers (`Sessions\Amounts`, `brick/math`) ; `FundingBalance::for()` pour la page, `FundingBalance::fundedOf()` pour la liste (une requête par page) ; un financement refusé ne compte pas.
- **Visibilité** : `SessionsVisibility::sessions()` / `dossiers()` par le périmètre du droit (`own` : responsable ou créateur ; `das` : `das_id`) ; les `Route::bind` (`trainingSession`, `dossier`, `enrolment`) répondent 404 hors périmètre. Les besoins d'adaptation et notes d'une inscription ne partent qu'à qui peut la modifier.
- **Historique** : pas de table, lu dans `audit_logs` (`History\SessionsHistory`) : fiches (dossiers selon `sessions.dossiers.view`, inscriptions d'une personne selon `sessions.sessions.view`) et page d'un dossier (dossier, inscriptions, financements, y compris supprimés). Ne journalisez jamais une valeur personnelle : `adaptation_needs`, `notes` sont dans `$auditPersonal`.
- **RGPD** : `Gdpr\EnrolmentAnonymisation` (besoins d'adaptation et notes des inscriptions, notes des financements et dossiers de particulier), `Gdpr\PersonSessionsExport`, `Gdpr\FicheReferences` (données liées, fusion). Une personne inscrite peut aller à la corbeille (inscriptions gardées).
- **Accueil** : `Sessions\StartingSoon` (« Sessions qui démarrent dans les 7 jours », périmètre `sessions.sessions.view`), lu par `DashboardController`.
- **Synthèse d'une session** : `Sessions\Summary\SessionChecklist` (`for`, `forMany` en requêtes groupées, `pending`) rend des `Card` (clé, état `done|todo|alert|na`, étape, ancre) selon le périmètre de l'utilisateur (financements : droit dossiers ; présences et clôture : droits présences) ; la page de la session (`SessionController::STEPS`, `?etape=`, `session-steps.tsx`) et les cartes du kanban lisent la même source.
- **Tâches et notes** : `Notes\SessionNotes` (tables `session_tasks`, `session_notes`, écriture sous le droit de modifier et hors session annulée, note modifiable par son auteur seul, texte dans `$auditPersonal`).
- **Colonnes** : `Sessions\SessionBoard::build()` réutilise `SessionListQuery` (une requête par état, 50 cartes, terminées sur 90 jours) ; le changement d'état glissé passe par `SessionStatusController` → `SessionWriter::setStatus` (planifiée ⇄ confirmée seulement, 409 sinon).
- **Séances dans Outlook** : `Planning\SeanceOutlook` déclare la source `sessions.seance` auprès de `Connectors\Calendar\OutlookSources` (registre ; `crm.activity` réservé) et appelle `OutlookSources::push` après commit ; `PushSourceToOutlook` relit l'état courant (`OutlookItem`) ; `calendar_link_events` est clé (`calendar_link_id`, `source`, `source_id`). Jamais de stagiaire, de note ni de prix dans l'évènement.
- **Fiche formation** : `Catalogue\TrainingBlocks` (registre, comme `FicheBlocks`) ; `Summary\TrainingSessionsBlock` y déclare le bloc Sessions (`SessionsServiceProvider::boot`) ; le Catalogue n'importe jamais Sessions.

## Planning individuel d'un stagiaire (2026-11-24) : points d'architecture à connaître

Code dans `tms/app/Modules/Sessions/Planning/` (`IndividualPlanning`, `IndividualPlanningWriter`, `EnrolmentAdjustment`, `IndividualPlanningView`, `IndividualPlanningController`). Guide : `tms/docs/sessions.md` (§ 3 « Planning individuel ») ; spec : `docs/superpowers/specs/2026-11-24-planning-individuel-stagiaire-design.md`.

- **Écarts** (`enrolment_adjustments`) : `exempt_seance`, `exempt_module` (séances futures comprises), `own_hours` (dans la séance), `added_seance` (séance d'une autre session). **`IndividualPlanning` est la seule source** de « qui est attendu à quelle séance, à quelle heure » : `expectedAt` (derrière `Attendances::expected`), `times` / `minutesAt` (présent = **sa** durée), `seancesOf` (planning, convocation, rappel, suivi), `exemptPairs`, `guestCounts`, `moduleCuts` ; aucune autre classe ne lit la table.

Crochet `Seances::onScheduleChange('sessions.individual_planning')` (déplacement, annulation, suppression : `SeanceChanged::DELETED`, jamais diffusé).

## Sauvegardes (0.8.2) : points d'architecture à connaître

Guide : `tms/docs/install.md` (« Sauvegardes », « Déménager vers un autre serveur »), `tms/docs/admin.md` (§ 17). Spec : `docs/superpowers/specs/2026-11-17-0.8.2-sauvegardes-design.md`.

- **Échange hôte ↔ application** : fichiers JSON dans `storage/ops/` du volume `storage`, **hors de `storage/app`** (jamais sauvegardés ni restaurés). `ops/backup.sh` écrit `backup-status.json` à chaque fin (réussie ou non, écriture atomique) et `backup-running.json` tant qu'il tient le verrou ; l'application écrit `backup-request.json` (`Core\Backups\BackupStatus`, `BackupController`, droit `settings.manage`, absent en mode multi). L'application n'a ni socket Docker ni secret restic.
- **Sauvegarde à la demande** : `tms-backup-request.path` (+ `.service`, `backup.sh --tag manuel`) créés par `enable_backup_requests` de `ops/lib.sh`, appelée par l'installateur et `update.sh` (idempotent) ; le verrou `/opt/tms/.ops.lock` reste la seule protection contre deux exécutions. L'unité supprime la demande avant de lancer `backup.sh` : si le verrou n'est pas obtenu, `backup.sh --tag manuel` la réécrit (`restore_backup_request`). Une demande de plus de 10 minutes (date du fichier) est périmée (`BackupStatus::requestStale`, nouvelle demande permise). L'application ne crée jamais `storage/ops` (l'hôte le fait). Pastille rouge sur « Sauvegardes » dans le menu (prop partagée `backup_alert`, `NavItem.alert`), jamais sur l'accueil, après 36 h (`BackupStatus::STALE_AFTER_HOURS`), échec ou état inconnu. `tms.ops_path` n'a pas de variable d'environnement (tests : `config()`).
- **Export / import** : `ops/export.sh [--output] [--stop]` (mot de passe saisi deux fois ou `TMS_EXPORT_PASSWORD`) produit un `.tar` contenant un dépôt restic autonome à un snapshot ; `ops/import.sh <fichier>` (`TMS_IMPORT_PASSWORD`) vérifie, fait une sauvegarde `pre-import`, restaure par `ops/restore.sh --with-app-key` puis `migrate.sh`, et refuse un export plus récent que la version installée. `restore.sh` lit `TMS_RESTORE_REPOSITORY` / `TMS_RESTORE_PASSWORD` (environnement seulement). `install.sh --import <fichier>` (ou `TMS_IMPORT_FILE`) : installation sans organisme ni administrateur, puis `import.sh`. Aucun mot de passe en argument ni dans un journal. Tests : `ops/tests/move.bats` (déménagement A → B), `backup.bats`, `install.bats`.
- **Copie hors site** : `restic_remote_copy` (`ops/lib.sh`) ; `RESTIC_REMOTE_REPOSITORY`, `RESTIC_REMOTE_PASSWORD`, `RESTIC_REMOTE_ENV_FILE`. Pour `sftp:`, `RESTIC_REMOTE_SSH_KEY` et `RESTIC_REMOTE_SSH_KNOWN_HOSTS` sont obligatoires, montés en lecture seule (`/run/tms/ssh_key`, `/run/tms/known_hosts`) et passés à chaque commande restic par `-o sftp.args=… StrictHostKeyChecking=yes BatchMode=yes` (jamais `=no`) ; seul leur chemin est affiché. Tests : `ops/tests/lib.bats` (docker simulé), `backup.bats`.
- **Déménagement** : `ops/export.sh --stop` arrête `app`, `worker`, `scheduler` **avant** la sauvegarde (redémarrés si l'export échoue), puis désactive `tms-backup.timer` et `tms-backup-request.path` et affiche la commande de remise en service. `import_mode_check` (`ops/lib.sh`) refuse un export multi-organismes vers une installation mono-organisme si le nombre d'organismes est > 1 ou inconnu.

## Module Finance (0.9) : points d'architecture à connaître

Code dans `tms/app/Modules/Finance/` (`Billing`, `Plans`, `Invoices`, `Settings`, `Integrity`). Guide utilisateur : `tms/docs/finance.md` ; réglages : `tms/docs/admin.md` (§ 3, § 10, § 18) ; tables : `tms/docs/data-dictionary.md`. Spec : `docs/superpowers/specs/2026-11-17-0.9-factures-design.md` (§ 4 et § 4 bis font autorité).

- **Frontières** : Finance lit Sessions par `Sessions\Public\Billing` (`dossier`, `hours`, `dossiersFor`, `lockDossier`, `allows`) et les fiches par `Crm\Public\Fiches::billingIdentity` ; il ne nomme aucune table de Sessions ni du CRM. Sessions, Crm, Catalogue, Core et Connectors n'importent jamais Finance (`ModuleBoundariesArchTest`) ; Finance se déclare aussi dans `Core\Companies\PrefixUsage` (préfixe déjà utilisé par l'autre type de pièce) ; Finance se déclare dans `Sessions\Public\DossierBlocks` (bloc Facturation), `BillingGuards` (`FUNDING_LOCKED`, `DOSSIER_TRASHABLE`, `PARTIES_LOCKED` société et contractant, `FUNDER_LOCKED` financeur d'un financement facturé : verrouillage après la première facture validée) et `DossierStates` (`markInvoiced` / `unmarkInvoiced`). Exceptions d'architecture : Finance ne référence, côté Connectors, que `Smtp\TenantMailer`, `Smtp\SmtpHostRefused`, `Core\ConnectorRun` et `Core\PermanentDeliveryFailure`.
- **Calcul** : `Billing\BillingCalculator::cumulative()` est **pur et statique** (aucune lecture de base ni d'horloge), en centimes entiers `brick/math` demi supérieur ; les parts des destinataires somment toujours à B (le contractant absorbe l'arrondi). `Invoices\Due` en tire le dû par destinataire (part cumulée − `Ledger`, qui ne somme que les lignes `computed` des pièces validées et avoirs ; lignes libres et mentions jamais) ; seuls les financements `agreed` avec `pays_directly` (ou `external_billing`) prennent une part ; dédit et absences vont au contractant seul, hors de B. Le mensuel ne facture que des mois clôturés ; l'échéancier ne facture les financeurs qu'à la dernière échéance.
- **Brouillons** : `InvoiceDrafts` sous `Billing::lockDossier()` (verrou de ligne du dossier, partagé avec les écrivains de Sessions), un brouillon ouvert par (dossier, `recipient_key`, type). Un avoir corrige toujours une facture validée du même destinataire (CHECK), en reprend la société et le destinataire (`Due` : `company_id`, refus à la validation sinon) et garde ses taux de TVA. « Recalculer » ne change jamais le type d'un brouillon (409). `BillingPlans::lock()` fige aussi la règle des absences résolue.
- **Validation** (`InvoiceValidator`, une transaction) : **ordre des verrous** = ligne du dossier → brouillon → plan de facturation (`BillingPlans::lock`) → `invoice_sequences` → verrou consultatif du journal de l'organisme. Re-contrôle du dû sous verrous, numéro `InvoiceNumbering` (`<préfixe>-<AAAA>-<NNNNN>`, exige une transaction, par société, type, année de Paris), destinataire figé, PDF rendu **dans** la transaction (échec Gotenberg = rollback, numéro rendu), puis un seul UPDATE et une ligne de journal.
- **Inaltérabilité** : déclencheurs `invoices_immutable` (seuls `status` validated→sent, `sent_at`, `email_status`, `email_error_code`, `updated_at` changent ; `recipient_key` est générée), `invoice_lines_immutable`, `invoice_journal_immutable`. Tout code qui touche une facture validée n'écrit que ces colonnes (jamais `updated_by`) ; une correction = un avoir.
- **Journal chaîné** : `Integrity::canonical()` (JSON trié, sans espaces), `hash = sha256(canonique . previous_hash)`, `invoice_journal.position` ordonne la chaîne, `pdf_sha256` (dans le contenu haché) détecte une archive remplacée ; `Integrity::verify()` = commande `tms:finance:verify` et bouton. Un PDF validé se sert toujours depuis l'archive (410 si perdue), jamais re-rendu.
- **Envoi** : `InvoiceSender` (verrou, 409 sur brouillon / envoi en cours / archive absente) → `SendInvoice` (`TenantAwareJob`, après commit, `TenantMailer`, refuse si l'archive ne correspond plus à `pdf_sha256`) ; `invoice_sendings` garde adresse, objet et message (jamais sur la facture figée) ; erreurs sans texte du serveur (`InvoiceMailFailed`).
- **RGPD** : une pièce validée est conservée 10 ans ; `InvoiceAnonymisation` (via `FicheLinks`) ne supprime que les brouillons. `notes`, `recipient_snapshot` et `description` de ligne sont dans `$auditPersonal`.
- **Montants** : jamais de flottant ; `Money` formate et analyse les centimes ; pénalités et 40 € seulement pour un destinataire `organisation`.
- **Facture libre et co-traitance** (spec `2026-11-20-facture-libre-mandataire-design.md`) : `invoices.origin` = `dossier` | `free` (CHECK : `dossier_id` nul exactement pour `free`) ; `FreeInvoices::create` (client = fiche, société, `buyer_reference`, `service_code`), lignes libres seulement, `invoice_lines.cotraitant_id` (fiche entreprise, sans FK). La validation, l'avoir (verrou de la facture corrigée au lieu du dossier) et le PDF sautent les contrôles de dossier. **Visibilité** : toujours par `Invoices\InvoiceAccess` (`allows`, `scope`) — une facture libre exige le périmètre « Tout ». `Integrity::canonical` n'ajoute `origin`, `buyer_reference`, `service_code`, `cotraitant_id` que s'ils sont renseignés (hash des pièces antérieures inchangé). Reversements : `cotraitant_payouts`, `Payouts\CotraitantPayouts` (dû = TTC des lignes co-traitées + avoirs validés, verrou de la facture), écran Finance › À reverser (`finance.payments.manage` + « Tout »).

## Règlements et relances (0.9.1) : points d'architecture à connaître

Guide : `tms/docs/finance.md` (§ 12 à § 15) ; réglages : `tms/docs/admin.md` (§ 10, § 18). Spec : `docs/superpowers/specs/2026-11-19-0.9.1-reglements-relances-design.md`.

- **RGPD** : `PaymentAnonymisation` (via `FicheLinks`) efface notes et référence des règlements d'un particulier ; montants gardés 10 ans.

- **Conventions d'alternance** (spec `2026-11-25-convention-alternance-design.md`) : `DocumentType::ApprenticeshipConvention|ProfessionalisationConvention` (`forContract`, `isAlternance`, `forCompany`), cadre `training-convention`. Le contrat parvient à Documents par `Sessions\Public\Paperwork::registerAlternance` (déclaré par Admissions, `AlternanceFacts`) → `Paperwork::dossier()['alternance']` ; une seule convention d'alternance vivante par dossier (tous types), la convention classique refusée en alternance. Émission à la création du dossier par `Sessions\Public\DossierHooks::onCreatedFromCandidature` (`Admission::createDossier($data, $by)`, après commit, échec journalisé) → `Documents\AlternanceConventions`. Aperçu avant le dossier par le registre `Core\Documents\Previews` (`alternance_convention`, `Documents\AlternancePreview`, prix et numéro « à compléter ») : Admissions n'importe jamais Documents.
- **Signature en ligne** (livraison 3, socle `Core\Signatures`) : `Signatures::request` (lien de 40 caractères, seul le sha256 gardé, 30 jours ; e-mail `signature_request` avec `{lien}`), `sendCode` (6 chiffres HMAC, 10 min, 5 essais, 1 par minute), `sign` (signature dessinée obligatoire, `SignatureDrawing` : PNG relu par GD, 200 Ko, non vide ; original et source vérifiés par sha256 ; la **source figée** `Core\Documents\PdfSource` (HTML exact archivé en `<pdf>.source.json` par `DocumentIssuer` pour les documents `signable()` et par `QuotePdf::archive`) est rendue à nouveau avec le dessin à la place de `PdfSource::SLOT` dans l'encadré ; sans source, l'original ; page de preuve `documents/signature-proof` fusionnée par `PdfRenderer::merge`, original jamais écrasé ; dessin archivé, effacé par l'anonymisation) ; évènement `SignatureCompleted` après commit, écouté par Documents (`DocumentSignatures`) et le Crm (`QuoteSignatures` : devis accepté, PDF signé = exemplaire signé, opportunité inchangée) ; `Signatures::registerGuard` permet au module propriétaire d'invalider un lien (devis qui n'attend plus de réponse). Page publique `signature/{token}` (`throttle:signature-public`, même page 404 pour tout lien invalide).
- **Documents des stagiaires** (livraison 2) : `DocumentType::perEnrolment()` (convocation, attestation, certificat du ministère non modifiable) ; `DocumentIssuer::issueForEnrolment` (`Paperwork::enrolment` : séances en clé `schedule`, heures réalisées) ; `DocumentBatch` (émission tout ou rien, envoi aux stagiaires ayant un e-mail, limité aux dossiers que l'utilisateur gère) ; page session par les registres `Sessions\Public\SessionBlocks` / `SessionCards` (`resources/js/components/session-blocks.tsx`) ; dossier « Convocations envoyées » quand tous les stagiaires attendus ont reçu la leur.

## Émargement en ligne : points d'architecture à connaître

Code dans `tms/app/Modules/Sessions/Attendance/Signing/`. Guide : `tms/docs/sessions.md` (§ 10 « Émargement en ligne ») ; tables : `tms/docs/data-dictionary.md`. Spec : `docs/superpowers/specs/2026-11-20-emargement-design.md`.

- **Demi-journée** (`SignSlot`, table `attendance_sign_slots`) = session × jour de Paris × `morning|afternoon`, coupure `Halves::CUT` (13 h) ; elle couvre les séances non annulées qui la touchent (`SlotSeances::of`), attendus = `Attendances::expected`. Ouverture **le jour même** (`AttendanceSigning::open`, nouveau jeton à chaque ouverture) ; jeton de 40 caractères, `token_hash` sha256 pour la recherche, `token_encrypted` (cast `encrypted`) seulement pour réafficher le QR (`SlotQr`, SVG bacon, aucun service externe).
- **Page publique** `emargement/{token}` (`PublicSigningController`, hors `auth`, throttles `attendance-signing*` **par jeton + adresse** : une classe partage une IP) : `findByToken` renvoie null pour tout cas invalide → même page 404 ; noms `publicNames` (« Léa D. »), jamais plus. Signature : `SignatureDrawing`, zone `TenantStorage` `attendance_signatures`, unique (créneau, inscription).
- **Validation** (`SlotValidation`, une transaction) : le valideur doit atteindre **toutes** les séances du créneau (`sessions.attendance.manage`, sinon 403 français) ; `validator_role` `trainer|manager`. Présences calculées sur les demi-journées **validées** de chaque séance (présent / partiel `Halves::minutes` / absent) et écrites par `Attendances::fromSigning`, qui ne touche que les lignes absentes ou `attendances.source = 'signing'` ; `Attendances::record` remet `source` à null (saisie à la main jamais écrasée). Mois clôturé = 409, rien n'est validé.
- **Ouverture par la séance** : `POST /seances/{seance}/signing-slots` (un formateur pur ne lie pas `{trainingSession}`) ; page formateur `sessions/emargement/{slot}` (404 hors périmètre d'une séance du créneau).
- **Feuille signée** (`SignedSheetPdf`, `SignedSheet`, gabarit `documents/attendance-signed-sheet`) : par session et mois, générée par un gestionnaire (périmètre ≠ « Ses séances »), chaque génération archivée (`attendance_sheets`) avec `pdf_sha256`, servie depuis l'archive vérifiée (410).
- **Connecteur futur** : `Sessions\Public\AttendanceSigning` (`slots`, `ensureSlot`, `recordExternal`, `validateExternal`, `source` ≠ `online`) ; rien dans Sessions ne nomme SoWeSign.
- **RGPD** : `SigningAnonymisation` (appelée par `EnrolmentAnonymisation`) efface dessins, IP, navigateur (heure gardée) et les feuilles d'une session individuelle ; export `emargements` dans `PersonSessionsExport`.
- **Rattrapage** (spec `2026-11-21-emargement-rattrapage-design.md`) : `attendance_signatures.kind` = `on_time` | `catch_up_onsite` | `catch_up_remote` ; seules les signatures `counted()` (à l'heure ou rattrapage confirmé) font la présence (`SlotValidation::writeAttendance`, `recompute`). `CatchUpConfirmation` (confirmer / refuser avec motif, gestionnaire hors « Ses séances », verrous session → créneau, mois ouvert). `OnsiteCatchUp` : jeton propre `catch_up_token_hash` d'un jour passé, jusqu'à minuit (`emargement/r/{token}`) ; `RemoteCatchUp` : `attendance_catch_up_links` (7 jours, usage unique, un lien actif par créneau et stagiaire, code e-mail HMAC 10 min / 5 essais / 1 par minute, `emargement/l/{token}`), e-mails `attendance_catch_up` / `attendance_catch_up_code` (`SendCatchUpMail`, `ShouldBeEncrypted`).

## Module Questionnaires (0.11) : points d'architecture à connaître

Code dans `tms/app/Modules/Questionnaires/` (`Surveys`, `Templates`, `Campaigns`, `Answering`, `Results`, `Gdpr`, `Settings`). Guide : `tms/docs/questionnaires.md` ; réglages : `tms/docs/admin.md` (§ 22) ; tables : `tms/docs/data-dictionary.md`. Spec : `docs/superpowers/specs/2026-11-20-questionnaires-design.md`.

- **Frontières** : lit Sessions par `Sessions\Public\Surveys` (`session`, `describe`, `trainees`, `traineeCounts`, `endDays`, `clientContacts`, `endedOn`, `allows`), le CRM par `Crm\Public\Fiches` / `FicheLinks`, le catalogue par `Trainings` ; s'affiche par `SessionBlocks` (`questionnaires.session`, `resources/js/components/questionnaires/session-surveys-block.tsx`) et `SessionCards` (`questionnaires.satisfaction`) ; satisfaction des fiches par le registre `Sessions\Public\EnrolmentSatisfaction` ; mesures par `Qualite\Public\Measures` (`SurveyMeasures`, indicateurs 30 et 2). Aucun module n'importe Questionnaires ni ne nomme ses tables (`ModuleBoundariesArchTest`, `QUESTIONNAIRES_TABLES`) ; une clé de props `people` ou `trainings` y est lue comme une table (d'où `trainees`, `training_options`).
- **Modèles** (`survey_templates`) : `SurveyContent::validate` (1 à 30 questions `rating|choice|text`), un défaut par type (`hot|cold`) et destinataires (`trainee|client`, index unique partiel), `DefaultTemplates::ensure()` crée les 3 modèles au premier usage seulement (jamais après une suppression). Une campagne **fige** les questions.
- **Lancement** (`SurveyLaunch::launch($sessionId, $kind, ?User)`) : verrou consultatif par session, une campagne par (session, type, destinataires), `inviteMissing` idempotent, lien QR (à chaud stagiaires : sha256 + jeton chiffré `Crypt`) ; à chaud, la campagne entreprise suit si son modèle est actif. Automatique (`$by` null) : silencieux ; manuel : `UserFacingHttpException` (409). Lien ouvert 30 jours (`LINK_DAYS`, Paris).
- **Envoi** : `SendSurveyInvitation` (`TenantAwareJob`, `ShouldBeEncrypted`, jeton en clair seulement dans la charge, après commit, `TenantMailer`, motif fixe sans texte du serveur) ; modèles d'e-mails `survey_hot|survey_cold|survey_client` (`{lien}` requis).
- **Réponse publique** (routes hors `auth`, `throttle:survey-public`) : `questionnaire/{token}` (lien personnel), `questionnaire/s/{token}` (QR : « Prénom N. » des non-répondants), puis `questionnaire/q/{invitation}` **signé** 2 h ; même page 404 (`public/survey`, état `invalid`) pour tout lien invalide, campagne close, session annulée ou à la corbeille. `SurveyAnswers::submit` : verrou de l'invitation, une réponse (409 sinon), `score` = moyenne des notes × 100 (`SurveyScoring`, demi supérieur ; satisfait ≥ 400).
- **Résultats** : `SurveyResults::campaign` (par question, textes sans nom), `SurveyOverview::rows|totals` (page `qualite/questionnaires`, export CSV `;` journalisé `questionnaires.results.exported`, mesures). Requêtes groupées pour les cartes.
- **Planifié** : `tms:questionnaires:daily` (7 h Paris, `ForEachTenant`, `DailySurveys`) : à chaud non lancé le lendemain du dernier jour, à froid à `ColdDelay::months()` (`tenants.settings.questionnaires.cold_months`, défaut 3, 0 = jamais) ; rattrapage 30 jours.
- **RGPD** (`Gdpr\SurveyPersonData` via `FicheLinks`) : données liées, fusion (une invitation par campagne, la répondue gagne), anonymisation (e-mail et réponses texte effacés, notes gardées, lien fermé par un nouveau hash), export (`questionnaires.view` requis sur « Tout »). Invitations et réponses ne sont pas `Auditable`.

## Automatismes et « À traiter » (2026-11-22) : points d'architecture à connaître

Guide : `tms/docs/admin.md` (§ 23) ; tables : `tms/docs/data-dictionary.md`. Spec : `docs/superpowers/specs/2026-11-22-deroulement-automatique-design.md`.

- **Socle** (`Core\Automation`) : `tms:automation:daily` (7 h 15 Paris, `ForEachTenant`) appelle le registre `DailyAutomations::register('cle', fn (CarbonImmutable $today): int)` ; chaque module déclare le sien dans son `boot` (Documents `convocations`, Sessions `day_before`, Core `signature_reminders`) ; une erreur d'un automatisme est journalisée (clé, classe) sans arrêter les autres. `AutomationSends::claim(kind, subjectId, occurrence)` (`automation_sends`, unique, `insertOrIgnore`) dans la transaction qui met l'envoi en file : rien ne part deux fois. Réglages `tenants.settings.automation` (`AutomationSettings`, relus à chaque appel), écran Administration › Automatismes + « Exécuter maintenant » (`RunAutomationsNow`).
- **Convocations** (`Documents\Automation\ConvocationAutomation`) : sessions **confirmées** dont la 1re séance est dans `[J+2, J+N]` (`Paperwork::confirmedSessionsStartingBetween`), stagiaires `Paperwork::sessionEnrolments` sans aucune convocation (une annulée n'est jamais refaite) ; émission et envoi **sans auteur** (`DocumentIssuer` / `DocumentSender` acceptent `?User`).
- **Attestations** (`Documents\Automation\CertificateAutomation`, `AutomationSettings::certificates`, désactivé par défaut) : sessions dont **tous** les mois de séances sont clôturés (`Paperwork::sessionsFinallyClosedSince`, part des clôtures récentes, rattrapage 30 jours), attestation + certificat de réalisation par stagiaire jamais émis, jamais pour 0 h réalisée (une annulée n'est jamais refaite), clé (`certificate`, inscription, `completion|realisation`).
- **Rappel la veille** (`Sessions\Automation\DayBeforeReminders`) : sessions confirmées, séances non annulées du lendemain ; stagiaires de `Attendances::expected`, formateurs (un e-mail par jour toutes sessions) ; personne à la corbeille, anonymisée ou sans e-mail : rien ; job `SendDayBeforeReminder` (`ShouldBeEncrypted`), jamais de prix ni d'autres stagiaires.
- **Relance des signatures** (`Core\Signatures\SignatureReminders`) : nouveau jeton à chaque relance (l'ancien lien meurt), `reminders_sent`, `last_sent_at`, garde du module (`Signatures::refusal`), pas de relance si code demandé < 24 h ; e-mail dans la transaction (échec = tout annulé).
- **À traiter** (`Core\Todo\TodoSources::register(key, group, label, permission, count, link, ?visible)`) : chaque module déclare ses lignes dans son `boot` (`SessionsTodo`, `CrmTodo`, `AdmissionsTodo`, `FinanceTodo`) avec la **même requête que l'écran lié** et le périmètre du droit ; une source en erreur = « Indisponible » ; total du menu en cache 60 s (`tenant:<id>:todo:<user>`, prop `todo_total`, null = pas d'entrée). Page `/a-traiter` en lecture seule.

## Conventions

- Identifiants UUID v7 ; suppression logique sur les fiches métier.
- Commits en anglais, style conventionnel (`feat:`, `fix:`, `chore:`, `test:`), petits et fréquents.
- Branche de travail par incrément (ex. `lot1a-socle`) ; ne jamais committer directement sur `main`.

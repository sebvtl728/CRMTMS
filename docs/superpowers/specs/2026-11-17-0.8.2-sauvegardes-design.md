# 0.8.2 — Sauvegardes : suivi dans l'application, export / import pour déménager

Validée par l'utilisateur le 2026-11-17 (« ok, vas-y » sur la proposition : page de suivi sans téléchargement, export/import par commande, guide de copie hors site). Base existante : `ops/backup.sh`, `ops/restore.sh`, minuterie `tms-backup.timer` (02:30), dépôt restic chiffré `/var/backups/tms`, copie distante `RESTIC_REMOTE_REPOSITORY`, alerte e-mail `TMS_ALERT_EMAIL` (voir `tms/docs/install.md`).

## 1. Intention

L'utilisateur veut être sûr de ne jamais perdre de données et pouvoir **réinstaller sur un autre serveur sans aucune perte**. Les sauvegardes nocturnes existent déjà mais sont invisibles dans l'application, et aucun moyen simple ne permet d'emporter un export d'un serveur à l'autre.

## 2. Objectifs, non-objectifs, anti-objectifs

- **Objectifs** :
  1. Page **Administration › Sauvegardes** (suivi) et bandeau d'alerte.
  2. Bouton **« Sauvegarder maintenant »**.
  3. **Export** en un seul fichier chiffré et **import** sur une installation neuve, sans perte (base, fichiers, connecteurs, 2FA).
  4. **Test automatique de déménagement** prouvant l'absence de perte.
  5. **Guide** de copie hors site (NAS en SFTP, stockage S3 compatible).
- **Non-objectifs** : téléchargement des données depuis le navigateur ; restauration lancée depuis l'application (reste une commande serveur) ; choix d'un fournisseur de stockage ; sauvegarde sélective d'un seul organisme.
- **Anti-objectifs** : un compte administrateur volé qui emporte la base ; une page qui affiche « ✓ » alors que la sauvegarde n'a pas tourné ; un import qui « réussit » avec des données manquantes ; un secret (mot de passe restic, `APP_KEY`) affiché dans l'application ou un journal.

## 3. Approches

- **A (retenue)** : le serveur reste maître. `backup.sh` écrit un **fichier d'état** que l'application lit ; l'application dépose une **demande** que l'hôte exécute ; export/import par scripts `ops/`. Aucun accès Docker ni secret dans le conteneur `app`.
- B : l'application pilote restic elle-même (secrets et socket Docker dans le conteneur) — refusé : élargit fortement la surface d'attaque.
- C : téléchargement de l'export depuis la page — refusé par l'utilisateur (risque de vol en un clic).

## 4. Décisions

### 4.1 Fichier d'état et demandes (échange hôte ↔ application)

- `ops/backup.sh` écrit à chaque fin (réussite **et** échec) `storage/ops/backup-status.json` dans le volume `storage` **hors** de `storage/app` (jamais sauvegardé ni restauré) : `{finished_at (ISO 8601), success (bool), snapshot_id, error (message français court, sans secret), version, size_bytes, remote: {configured: bool, success: bool|null}, snapshots: [{id, time, tags}] (liste du dépôt local après rétention, au plus 60)}`. Écriture atomique (fichier temporaire puis renommage).
- « Sauvegarder maintenant » : l'application écrit `storage/ops/backup-request.json` (`{requested_at, requested_by_id}`) ; un **`tms-backup-request.path`** systemd (surveille le fichier) ou à défaut une minuterie toutes les 2 minutes lance `ops/backup.sh --tag manuel` puis supprime la demande. Une demande déjà en attente ou une sauvegarde en cours : le bouton est désactivé (« Sauvegarde en cours… »). Le verrou existant `/opt/tms/.ops.lock` reste la seule protection contre deux exécutions.
- L'installateur et la mise à jour créent `storage/ops` (propriétaire = utilisateur du conteneur app, lecture/écriture) et installent l'unité de demande.

### 4.2 Page Administration › Sauvegardes

- Droit **`settings.manage`** (administrateur, 2FA déjà obligatoire). En mode **multi-organismes** (`config('tms.mode') === 'multi'`), la page et le bandeau n'existent pas (l'hébergeur gère le serveur).
- Contenu : état de la dernière sauvegarde (date en heure de Paris, réussie / échouée avec le message, taille, version, identifiant court), copie hors site (configurée ou non, résultat de la dernière copie), liste des sauvegardes disponibles (date, étiquettes : `manuel`, `pre-update-…`, `version:…`), bouton « Sauvegarder maintenant », rappel « Conservez le mot de passe des sauvegardes et la clé de l'application hors du serveur » avec lien vers le guide.
- **État inconnu** (fichier absent, illisible) : « Aucune sauvegarde connue » en alerte, jamais ✓.
- **Bandeau** d'accueil pour les détenteurs de `settings.manage` : dernière sauvegarde échouée, ou réussie il y a plus de **36 heures**, ou inconnue → « La dernière sauvegarde … » avec lien vers la page.
- Journal d'audit : « Sauvegarde demandée » (qui, quand).

### 4.3 Export et import

- **`ops/export.sh [--output <dossier>]`** : lance une sauvegarde étiquetée `export` (réutilise `backup.sh`), puis crée un **dépôt restic autonome** contenant ce seul snapshot (`restic copy`), protégé par un **mot de passe d'export** saisi au clavier deux fois (ou `TMS_EXPORT_PASSWORD`, jamais en argument), et l'archive en **un fichier** `tms-export-<organisme ou hôte>-<AAAAMMJJ-HHMM>-v<version>.tar` (mode 600) avec une empreinte SHA-256 affichée. Le fichier contient la base, les fichiers, l'`APP_KEY` et la version (chiffrés par restic). Dernière ligne affichée : le chemin du fichier.
- **`ops/import.sh <fichier>`** : sur une installation existante (neuve ou non), demande le mot de passe d'export, vérifie le fichier (lisible, un seul snapshot, version ≤ version installée sinon refus clair « mettez d'abord à jour en <version> »), fait une **sauvegarde de sécurité** de l'état courant, puis restaure via `ops/restore.sh --with-app-key` sur ce dépôt temporaire, lance les migrations (`ops/migrate.sh`, l'export peut venir d'une version plus ancienne) et `tms:permissions:sync`, attend `/health`, puis affiche un **récapitulatif de contrôle** (nombre d'organismes, utilisateurs, entreprises, personnes, sessions, fichiers).
- **`install.sh --import <fichier>`** (ou réglage `TMS_IMPORT_FILE`) : installation neuve sans création d'organisme ni d'administrateur, puis `import.sh`. Les nouveaux secrets techniques (PostgreSQL, Redis, restic) sont ceux du nouveau serveur ; l'`APP_KEY` est reprise de l'export.

### 4.4 Test de déménagement (bats, pile jetable)

Pile A : données de démonstration + fichiers + un secret de connecteur chiffré + 2FA d'un utilisateur ; `export.sh`. Pile B neuve : `install.sh --import` (ou `import.sh`). Contrôles : nombre de lignes **de chaque table** identique (lecture en super-utilisateur, RLS contourné), même somme de contrôle de l'arborescence `storage/app`, secret du connecteur déchiffrable, 2FA vérifiable, `/health` vert. Cas d'erreur : mauvais mot de passe, fichier tronqué, export d'une version plus récente → refus, rien n'est modifié.

### 4.5 Guide hors site

`tms/docs/install.md` § Sauvegardes : copie automatique vers un **NAS en SFTP** (`RESTIC_REMOTE_REPOSITORY=sftp:user@nas:/tms-backups`, clé SSH dédiée) et vers un **stockage S3 compatible** (`s3:…`, identifiants dans `RESTIC_REMOTE_ENV_FILE`), comment vérifier sur la page, et procédure complète de **déménagement** (export, copie, installation `--import`, contrôle, mise à jour du DNS). `tms/docs/admin.md` : la page Sauvegardes.

## 5. Contraintes

Règles du projet (CLAUDE.md) : français ; aucun secret dans le dépôt, les journaux, l'application ou les arguments de commande ; scripts `shellcheck -x` propres et testés par bats ; ASVS niveau 2 ; heure de Paris à l'affichage. Le conteneur `app` n'obtient ni socket Docker ni secret restic.
